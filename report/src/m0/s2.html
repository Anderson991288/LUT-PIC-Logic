承接：M0 s1 確認工具都能用，並寫出第一份結果 env.json。

本步要回答：之後每一步都會產生數字、圖和程式。怎樣讓報告上的數字永遠和計算結果一致，而且不必靠人工逐一核對？

交給下一步：組裝程式、檔案索引、共用的符號表（附錄 A），以及一套證明「檢查確實能檢出錯誤」的測試。從 M1 起，每一步只需撰寫片段並執行組裝。

名詞對照：片段（fragment，每個步驟一個 HTML 原稿）、組裝（build，把片段組成可讀的分頁報告）、故障注入（fault injection，故意放入錯誤，確認檢查會發現）

① 問題與範例

範圍：本步處理報告工具，與光學原理無關。以光運算為主要目的的讀者可略過本步，直接進入 M1。

學習目標：了解報告的產生流程，會寫一個符合格式的步驟片段，並知道組裝時會自動檢查哪些事。

類比：報告像一本食譜，數字是「鹽 5 g」。如果改了配方卻忘了改食譜，讀者照著做就會失敗。解決方法是食譜上不手抄數字，而是寫「鹽＝配方表第 3 列」，印出時自動代入最新值。

實際的例子在本步就發生了：M0 s1 的報告原本手寫「執行約 73 秒」，第二次執行只花 6 秒，手寫的數字立刻過時。這個錯誤是下面故障注入測試的「原片段不誤報」案例檢出的：它要求片段的備用值（寫在數字標籤內的文字，組裝時由 JSON 覆寫）與 JSON 完全一致。

② 原理與推導

本步沒有物理公式，重點是「單一來源」原則：每個事實只存在一個地方，其他地方都引用它。

事實唯一來源引用方式
計算結果的數字各步驟 out/*.json片段寫 <span class="num" data-json="…" data-expr="d['passed']">，組裝時重算
檔案位置design/paths.py程式用 OUT("m0_env/s1_check", "env.json")，不寫絕對路徑
符號與埠名PLAN.md 的「符號表」組裝時產生附錄 A
名詞在哪一步首次定義PLAN.md 的「名詞首次定義」表組裝時檢查：名詞不可出現在定義步驟之前
步驟清單與進度PLAN.md 的「步驟表」組裝時產生入口頁的學習路線與步驟目錄
修改歷史各步驟 HISTORY.md組裝時帶入附錄 B

附錄 B 是維護用的開發紀錄，不是教材，初次閱讀可略過。其中「M0 審查 R5」這類編號是當時審查項目的流水號，「本次重跑」是重建專案時的紀錄。

PLAN.md 是專案根目錄的課程計畫檔（Markdown），組裝程式依段落標題找表格，每張表第一列是欄名。新增時照下面的格式加一列：

表（段落標題）欄位範例一列
## 符號表符號｜意義｜單位| P_u | 一路資料「1」在 B7 輸入端的功率 | — |（底線後的字組裝時變成下標）
## 名詞首次定義名詞｜定義步驟| ΔP | M1 s1 |
## 步驟表步驟｜標題｜問題｜成果｜時數｜對照｜驗收｜狀態狀態欄第一個字 ☐／◐／☑ 決定入口頁的進度標示

儲存格內要寫直線（例如 |y2|²）時寫成 \|，否則會被當成分欄。

組裝流程：片段 → 格式檢查（銜接框、六節順序）→ 帶入 JSON 數字、程式、歷史 → 改寫圖片路徑 → 產生入口頁、各里程碑頁、附錄頁 → 禁字（讀者文件不該出現的字，例如本機路徑）與連結檢查 → 有任何錯誤就不寫檔。

③ 動手做

  1. 組裝報告：
    .\lab tools\build_report.py
    預期輸出「寫出 N 頁（…個步驟片段）」。若出現「錯誤：」開頭的行，依訊息修正片段後重跑。
  2. 更新檔案索引：
    .\lab tools\make_index.py
    產生 design/INDEX.md，列出每個檔案的大小、用途與產生它的程式；找不到產生者的檔案標「？」。
  3. 驗證檢查本身：
    .\lab design\m0_env\s2_tools\test_tools.py
    取 M0 s1 的真實片段，先把片段裡的備用值換成這台電腦的 JSON 值（換一台電腦、版本不同時測試仍成立），再每次注入一種錯誤，確認組裝程式會發現。

之後各步 ③ 列出的 figs.py 只負責畫該步的圖。

實際遇到的錯誤與修正：

  • 名詞先用後定義：校閱時發現 M0 s1 介紹 MMI 時，直接用了 M1 才會教到的兩個名詞，讀者讀到這裡還不知道它們是什麼。改寫該句，並新增「名詞首次定義」表與對應檢查：表中的名詞若出現在定義步驟之前，組裝就報錯。
  • 附錄 A 沒產生：第一次組裝時附錄 A 不見了。原因是計畫的段落標題寫成「符號表（全計畫共用…）」，程式只認「符號表」四個字。修正為允許標題後有附註。
  • |y2|² 被切成兩欄：表格用直線分欄，符號裡的絕對值直線被當成分欄。修正為先保護跳脫的直線再分欄；修改歷史表也套用同一個修正。
  • M0 s1 的執行時間過時：第一次執行 73 秒，之後 6 秒。執行時間每次不同，不適合當驗收數字，改成文字說明。
  • 圖 M0-1 找不到產生者：圖原本是在指令列另外產生的，索引無法追溯。改由環境檢查程式自己產生，重跑就能重現。
  • 補強的檢查：複查時發現五個漏洞，都已修正：(1) 禁字只比對大小寫完全相同的字，小寫的資料夾名與大寫的計畫代號都漏掉；(2) Python 字串中雙反斜線的本機路徑、網路路徑、環境變數路徑沒有檢出；(3) 同頁錨點完全沒檢查；(4) 索引用檔名片段比對產生者，過時檔可能被誤認為有產生者。(5) 測試固定寫入這台電腦的「13／13」，換一台電腦就會失敗；改為先用當地的 JSON 更新備用值。
  • 索引把自己的說明當成輸出清單：索引程式的說明文字裡有一句「docstring『輸出：』段落」，被誤認為輸出清單的開頭，導致 index_stats.json 找不到產生者。修正為只認行首的「輸出：」。

檔案索引中，M0–M3 主課程找不到產生者的檔案有 0 個，都是商用工具實跑留下的紀錄。全專案找不到產生者的檔案共 0 個，多半是執行紀錄、商用工具輸出與教材來源（這個數字會隨課程進度增加，所以不列為驗收數字）。

⑤ 常見錯誤與自我檢查

  • 直接改成品 HTML：下次組裝就被覆蓋。只改 report/src/ 的片段。
  • 把每次都不同的量當驗收數字：執行時間、檔案修改時間會變，應寫成範圍或文字。
  • 以為測試全過就代表檢查有效：測試要包含「不注入錯誤」的案例，才知道檢查不會誤報；也要包含確實發生過的錯誤，防止再犯。
自我檢查 1：如果換了一台電腦重跑 M0 s1，env.json 的通過項數從 13 變成 12，報告要改哪裡？

報告不必手改：片段引用 JSON，重新組裝就會顯示 12／13，並提示原稿的備用值過時（故障注入測試也不受影響，因為它先用當地的 JSON 更新備用值）。要處理的是環境本身：查出哪一項失敗、為什麼。

自我檢查 2：為什麼故障注入要一次只注入一種錯誤？

一次注入多種錯誤時，只要其中一種被檢出，案例就會「通過」，無法確認每一種檢查都有效。
