承接：M3 s5 交出交付包；其中的 chip.gds 已用 KLayout 與平台 deck 驗證 DRC 0。業界的晶片設計多半在 Virtuoso 中管理佈局、用 Calibre 做 DRC，接手的人很可能用這兩套工具打開這份 GDS。

本步要回答：把同一份 GDS 交給 Virtuoso 與 Calibre，結果和 KLayout 一樣嗎？從 Virtuoso 再匯出一次，幾何會不會變？KLayout 的規則能不能直接搬到 Calibre？

交給下一步：commercial.json（Calibre 草案在四份 GDS 上的結果、兩次匯出後 KLayout 的結果、逐層幾何比對）與兩個給接手者的提醒。第一，從 Virtuoso 匯出 GDS 時用 maxVertices＝8191。第二，兩套工具結果不同時要先追出原因，Calibre 草案不能取代平台 deck。本步是課程的最後一步，這兩點寫在本步的結論。

名詞對照：Virtuoso（業界常用的佈局與電路設計環境）、OA（OpenAccess，Virtuoso 存放設計資料的資料庫格式）、strmin／strmout（Virtuoso 把 GDS 匯入成 OA、再由 OA 匯出成 GDS 的批次指令，屬於 XStream 工具）、maxVertices（匯出時每個多邊形允許的最多頂點數；超過就切成多塊）、Calibre（業界常用的 DRC／LVS 工具）、SVRF（Calibre 的規則檔語言）、Calibre 草案（本步由 KLayout deck 自動轉出的 SVRF 規則檔，未經晶圓廠驗證）、對稱差（兩份幾何互不重疊部分的面積）、合併（merge，檢查前把相接或重疊的多邊形聯集成一塊；不合併就是一塊一塊分開檢查）

① 問題與範例

學習目標：能用批次指令完成 Virtuoso 的 GDS 匯入與匯出、Calibre 的 DRC；能說明匯出參數 maxVertices 如何改變幾何；能說明「把規則從一套工具移植到另一套」為什麼需要驗證；兩套結果不同時，能用小實驗追出原因。

類比：一份文件用 A 文書軟體寫好、檢查過拼字，再用 B 軟體開啟另存一次。另存時 B 可能把長段落切成好幾段，看起來一樣，排版細節卻變了。這時 A 的檢查若是「一段一段分開看」，會在每個切口報錯；B 若是「整篇接起來看」，就不會報錯。兩邊結果不同，不代表哪一邊比較嚴格，要先弄清楚各自看的是什麼。所以換工具時，要用同一批文件交叉比對兩邊的結果，並追出不同的原因。

② 原理與推導

1. 規則移植

平台 deck 有 24 個輸出敘述（.output），執行後產生 30 個檢查類別（M3 s3、s4 寫的「30 條規則」）：其中格點檢查是一個迴圈，對 7 個層各產生一個類別。24 個敘述中，8 個層的最小線寬與最小間距共 16 個，其餘 8 個是格點、設計區、重疊與小特徵（逐條列在 ⑥）。本步只把這 16 個自動移植成 SVRF：線寬用 INTERNAL、間距用 EXTERNAL，門檻沿用 deck 的值加上 deck 本身的 −0.001 µm 容差。這份草案沒有經過晶圓廠驗證，兩套工具在角度、面積為 0 的結果與多邊形合併上的寫法也不同（⑥ 的對照表），所以它只能當交叉檢查，不能取代平台 deck。

2. 匯出時的多邊形切割

GDS 規定一個多邊形最多 8191 個頂點，但 Virtuoso 的 strmout 預設只用 200。本晶片的彎道（S 彎、補長段的凸起）用數百個頂點描述，超過 200 時會被垂直切成好幾塊。斜的波導被垂直切開，每一塊在切口處都有一個銳角；拼回去（合併）之後，切口不會留下縫，形狀與原檔只有極小的差異（④ 的對稱差）。所以檢查是看一塊一塊的多邊形，還是看合併後的形狀，結果就會不同：逐塊看時，切口的銳角像一條極窄的線，會被判為線寬不足。

3. KLayout 的合併與 .raw

KLayout 的 DRC 預設先合併再檢查，Calibre 也是。但 KLayout 有一個容易忽略的寫法：層.raw 會把「這個層物件本身」改成不合併模式，而不是只影響這一行。平台 deck 檢查 GDS 6／60（本晶片沒有使用的兩層）與 GDS 3 的重疊時寫了 soi_etch2_light_layer.raw.sized(0.2.um)（soi_etch2_light_layer 就是 GDS 3，.clean 是改回合併模式的寫法），此後同一個 GDS 3 物件的線寬、間距檢查，也就都變成逐塊檢查。

結論：交付的 GDS 在 Calibre 草案下同樣是 0 違規，故意的違規兩邊都能檢出。maxVertices＝200 的匯出檔兩邊結果不同，原因已用小實驗確認。有兩件事要提醒接手的人：

  1. 從 Virtuoso 匯出時用 maxVertices＝8191。預設的 200 會把彎道切成多塊。合併後切口不留縫，形狀與原檔只有極小的差異（④ 的對稱差），不是製造上的錯；但平台 deck 對 GDS 3 逐塊檢查，會在每個切口報錯（33 處），投片前若用同一份 deck 檢查就會被擋下，而且多出的分塊只會增加檔案的複雜度。8191 則與原檔完全相同。
  2. 33 對 0 的原因是「平台 deck 不合併 GDS 3」，不是 Calibre 漏抓。小實驗中，同一份檔案在合併狀態下 0 處，呼叫 .raw 之後變成 32＋1＝33 處，和平台 deck 完全相同；Calibre 預設合併，所以 0 處反映的是合併後、也就是實際製造的形狀。即使如此，草案仍不等於平台 deck：只移植了 16/24 個敘述，角度、面積為 0 的結果與合併的寫法也不同（⑥ 的對照表）。所以 Calibre 草案只能當交叉檢查；投片前仍以平台 deck 與晶圓廠的正式檢查為準。

實際遇到的情況：本步的批次流程第一次執行就完成。第一版的結論是「平台 deck 能檢出、Calibre 草案檢查不出，只用 Calibre 會誤以為沒問題」，並推測切口有 nm 級的取整差。重新檢查 deck 後確認 .raw 會改變 GDS 3 本身的合併狀態；加上小實驗後確認：切口兩側完全接上，33 處全部來自逐塊檢查。教訓是：兩套工具結果不同時，不要預設比較嚴格的那一邊就是對的，要先用最小的實驗找出差在哪裡；一個檢查報「0」或報「33」，都要知道它看的是什麼形狀。

執行環境：EDA 伺服器（一台裝有 Virtuoso 與 Calibre 的 Linux 環境）上的 Virtuoso IC23.1（strmin、strmout）與 Calibre 2026.1；批次執行、不開 GUI，Calibre 最多 4 執行緒。.raw 小實驗在本機 KLayout 執行。

⑤ 常見錯誤與自我檢查

  • 用預設參數匯出：maxVertices＝200 會切割彎道；光子晶片的曲線多，要改成 8191。
  • 以為規則換個語法就一樣：不同工具對角度、面積為 0 的結果、合併的處理不同，移植後要用同一批檔案（含故意的錯）比對兩邊結果。
  • 以為 .raw 只影響這一行：KLayout 的 .raw／.clean 會改變層物件本身，後面所有用到這個物件的檢查都受影響。
  • 只看數字、不問原因：一個檢查報 0，可能是確實沒錯，也可能是規則漏了；報 33，也可能是看的形狀和實際製造的不同。兩套結果不同時，要用小實驗找出原因。
自我檢查 1：為什麼 maxVertices＝8191 的匯出檔和原檔完全相同？

本晶片最多頂點的多邊形也不超過 8191，所以匯出時不需要切割，每個多邊形原樣寫出；逐層比對塊數相同、對稱差面積為 0，cell 名稱與文字標記也相同。注意這個比對只看幾何、cell 名稱與文字標記，不含 GDS 的其他屬性。

自我檢查 2：Calibre 草案在「故意違規」的檔案上報 2 處，這能證明它和平台 deck 等價嗎？

不能。它只證明這兩種違規（Ti/AL 太窄、TiN 太近）能檢出。草案只移植了 16/24 個敘述，角度與面積為 0 的寫法和平台 deck 不同；maxVertices＝200 的匯出檔上兩邊結果也不同（原因是平台 deck 逐塊檢查 GDS 3，草案合併後檢查）。等價要逐條比對語意，並用更多已知有錯的檔案測試。

自我檢查 3：如果接手的人只用 Virtuoso 與 Calibre，應建議他如何做？

直接用交付的 chip.gds（不要經 Virtuoso 匯出後再交出去），或匯出時設 maxVertices＝8191 並與原檔比對幾何；DRC 以平台提供的正式 deck 為準，Calibre 草案只當輔助。
