承接：M3 s4 確認晶片可製造（DRC 0）、電氣與光學連接都和規格一致（LVS 14/14、光學 10/10）。M2 s1 的需求 K1 要求：晶片完成後依量測重新求相位，並重算容許範圍。

本步要回答：把晶片交給別人（量測者、封裝廠、下一個接手的人）時，要交哪些檔案與說明？對方如何知道如何接光、接電、校正？如何確認收到的檔案沒壞、彼此一致？

交給下一步：根目錄的 delivery/ 交付包（佈局、介面、驗證結果、圖、README、交付檢查程式、雜湊清單）與交付檢查結果 delivery_check.json。這是整個課程的最終成品；M3 s6 再以商用工具對照同一份 GDS。

名詞對照：交付包（給別人使用的一組檔案與說明）、雜湊清單（manifest，列出每個檔案與它的 SHA-256，用來確認檔案沒有被改動或損壞）、自我測試（self-test，檢查程式先對故意改壞的副本執行，確認它確實會報錯）、反向測試（negative test，餵給檢查程式不該通過的資料，例如刪一列、複製一列、空集合，確認它會拒絕）

① 問題與範例

學習目標：能決定交付包應包含哪些檔案與說明；能寫出一個只依賴交付包本身的檢查程式；能用雜湊與交叉比對確認檔案一致；能把前面各步的限制整理成接手者可依循的操作與校正步驟。

類比：買來的家具要附上零件清單、組裝說明和保固條款。零件清單讓你點收（缺了什麼、拿錯了什麼）；組裝說明讓你不必打電話問廠商；保固條款寫清楚哪些情況不保證。交付包也一樣：雜湊清單是零件清單，README 是組裝說明，已知限制是保固條款。

最好的交付包，是對方不必看前面十幾個步驟的程式，也不必問作者，就能把晶片用起來。

② 原理與推導

1. 交付包要回答三件事

問題對應檔案
是什麼layout/chip.gds、figures/、README 第 1 節
如何接、如何用interfaces/（規格、PAD 對照、EC 對照、接線表、相位起點、驗收答案）、README 第 3–5 節
為什麼可信、哪裡不保證verification/（DRC、LVS、審查、模擬）、README 第 6–7 節

2. 用雜湊確認完整與一致

SHA-256 把一個檔案算成 64 位十六進位碼；檔案改一個位元組，碼就完全不同。交付包用它做兩種確認：

  • 完整：MANIFEST.json 列出每個檔案的雜湊；接手者重算一次，對得上才表示沒有缺檔、沒有損壞。
  • 一致：chip.gds 的雜湊必須等於 DRC 與連接檢查結果裡記錄的雜湊，才能說「這些驗證是對這份 GDS 做的」；接線表的雜湊必須等於相位設定檔記錄的雜湊，相位才適用（M1 s5 的做法）。

3. 自己重算，而不是只相信結果檔

交付檢查程式不用課程的共用模組，而是用自己的幾行矩陣運算，從接線表與相位設定檔重算 80 組 ΔP，再和真值表比對。這是另一條獨立的計算路線（先前已有 M1 的矩陣乘法、M2 s3 的電路模擬與 M3 s2 的佈局抽取），接手者可以自己驗證「這些相位確實能讓這個光路做出這些函數」。

4. 數量對，不代表集合對

只比數量、或只看「全部為真」，會放過兩種錯：同一列重複 80 次，數量還是 80；清單被清空時 all([]) 為真，「全部通過」也成立。雜湊擋不住這些錯，因為改檔的人可以順手更新 MANIFEST.json。所以檢查程式把完整的集合寫死在程式裡，不從受檢的檔案推出來：18 個檔案、21 個 PAD、14 個 heater、10 個 EC 埠、5 個函數 × 16 組輸入、8 種故障案例；逐一比對有沒有重複、缺少、多出。真值表的 target 也由函數定義算出，不相信檔案自己寫的答案。

實際遇到的情況：複查時發現兩點。(1) 在課程內執行檢查時，不加 --self-test 也會寫結果檔，把自我測試的紀錄蓋成空的；改成只有完整檢查才寫。(2) README 原本寫「只送一路光標定每個 heater」，但 φ 是 MZI 兩個輸入之間的相對相位，只有兩個輸入都有同源光時才看得到；改寫成 θ 用單路光、φ 用兩路同源光標定。README 也補上座標原點、PAD 間距不等、損耗估計與 Pπ 的出處。

外部審查又發現：把第二筆 EC 複製成第一筆，K5 仍通過「10 個 EC」；同一列真值表重複 80 次，K8 仍通過「80/80」；光學驗證列與故障注入結果清空，K9 也通過。原因是只比長度、以及 all() 對空集合為真。改成和固定清單比對後，第一次跑自我測試時所有竄改都顯示「抓到」，但「未改動的副本」未通過：比對函式把字典交給 Counter，字典的值被當成次數而出錯，程式錯誤也判成未通過。所以自我測試要先跑未改動的副本，也要看未通過的原因，不能只看「抓到」的數量。

⑤ 常見錯誤與自我檢查

  • 只交 GDS：沒有 PAD 對照、相位起點與校正步驟，接手者無法使用。
  • 驗證結果和交付的 GDS 不是同一版：沒有雜湊對照時，很容易交出改過之後沒有重新驗證的 GDS。
  • 只比數量，或用 all() 判全部通過：重複的資料數量不變，空集合會讓 all() 為真；要和完整的鍵集合比對，也要測刪列、複製列、空集合。
  • 交付檢查依賴作者的環境：檢查程式應只依賴交付包本身與常見套件，否則別人無法執行。
自我檢查 1：如果有人改了 chip.gds，也同時更新了 MANIFEST.json，哪個檢查會檢出？

K6：chip.gds 的雜湊會和 drc_result.json、connectivity.json 記錄的不同，表示驗證結果不是對這份 GDS 做的（自我測試的「GDS 被改」就是這一種）。

自我檢查 2：README 第 5 節為什麼要先量電阻，再做 heater 標定？

電阻決定電流與電流密度（M3 s3 只能假設 0.5–2 kΩ），也能確認 14 個 heater 都導通、7 個 GND PAD 都有接上；這些確認之後，掃描 heater 功率得到的週期變化才有意義。

自我檢查 3：交付包中為什麼同時放 spec.json 和 pads.csv？

spec.json 是規格（heater 與 PAD 的對應），pads.csv 是實際佈局（PAD 在哪裡、接哪個 heater）。檢查 K4 比對兩者，確認佈局照規格做；接手者接探針時則直接使用 pads.csv 的座標。
